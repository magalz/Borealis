# Working on Borealis

Borealis is a game-streaming client built on Moonlight and tailored to the LuminalShine host. Use English for source, documentation, commits and product text. Versioned [ADRs](docs/adr/README.md), the [host contract](docs/host-contract/README.md) and the [development guides](docs/development/README.md) are canonical.

## How work is organized

- The main Claude session (Opus) orchestrates. Exploration goes to the `br-scout` subagent (Haiku), light text work (PR descriptions, release notes, changelog entries, issue text, ADRs from orchestrator notes) to `br-scribe` (Haiku), implementation tasks to `br-implementer` (Sonnet, extra high effort), and independent checks to `br-reviewer` (Sonnet, extra high effort), as described in [orchestration](docs/development/orchestration.md). Briefs follow the [task brief template](docs/development/task-brief.md).
- Use Memtrace first for code discovery, impact and history when its tools are connected (`repo_id: Borealis`). Entire Brain (`entire brain …`, see `.entire/agent-guide.md`) answers why code is the way it is and what was decided or tried before (`entire brain recall`), and it is the fallback for code questions: when Memtrace is unavailable or answers wrong and Brain can answer (`entire brain inspect …`), ask Brain before targeted Grep and ranged reads. If either is unavailable or inconsistent, say so and continue; Brain's answers, like Memtrace's, are leads, and its index can trail the checkout (`entire brain status`). Memtrace's main use is impact analysis: `get_impact`, `preflight_check` and `detect_changes` before an edit. Versioned documents stay canonical; Memtrace results are not verification evidence. Its dead-code and duplicate-code results are leads: a deletion needs a manual check for callable references (`::f`), Compose, JNI, the manifest, reflection and Hilt.
- This holds for every subagent that explores code too (`br-scribe` has no Memtrace tools): each loads the `memtrace-skills:memtrace-first` skill before exploring. Memtrace (1.2.10 and later) indexes a checkout only under the branch it has checked out, so the orchestrator's checkout is indexed with its own branch: the phase branch while a phase runs (for example `branch: "phase/s11-appearance"`), and `main` after the owner merges. Indexing the new phase branch on the commit already indexed as `main` reuses those records, so it takes a few minutes and computes no new embeddings (about 3.5 minutes on 2026-10-23). The orchestrator re-runs that incremental index after each merge wave. The daemon runs with `MEMTRACE_NO_STARTUP_WATCH=1` and `MEMTRACE_NO_WATCH_RESTORE=1`, so no watcher records live edits, and we do not call `watch_directory`: answers reflect the last index of the checkout. Every Memtrace call passes the indexed branch when the tool takes one (`get_symbol_context`, `analyze_relationships`, `get_impact`, `detect_changes` and the quality tools), because the store keeps older copies of the repository under other labels: a call without the branch mixes them and comes back ambiguous, empty or slow. `find_symbol`, `find_code` and `preflight_check` take no branch; scope them with `repo_id` and, when needed, `file_path`. When two symbols share a name, pass `file_path` or the `node_id` from an earlier result; a Java class and its constructor share a name, so `get_symbol_context` on a Java class takes the class `node_id` as `symbol`. The graph has no Kotlin-to-Java call edges, so the Kotlin callers of a Java class are found with Grep. `preflight_check` and `get_impact` have no size limit: on a widely used symbol they return over 200,000 characters, so prefer `get_symbol_context` with `limit` there. One index job runs at a time per repository: an index sent while another runs answers `busy` with `retry_after_s`, and heavy reads during an index can make it fail with `os error 33`, so the orchestrator indexes when no agent is querying. A task worktree is an overlay with its task branch: the orchestrator indexes the worktree once (`index_directory` with the worktree `path`, `repo_id: Borealis`, the task `branch`, `incremental: true`) and the subagent passes `worktree: "Borealis:<worktree folder name>"` (exact id from `list_worktrees`) to `find_code`. Every path Memtrace returns is mapped to the subagent's own worktree before it reads or edits the file.
- At the end of every sprint, after the owner merges the phase, the orchestrator removes the task worktrees, checks out `main`, wipes the whole Borealis store and indexes the checkout again from scratch as `branch: "main"`. In `D:\Repos\Borealis`, it runs `memtrace stop`, `memtrace reset` with no repository (it empties `.memdb` and moves its history to `.memdb.history`), `memtrace history purge --store D:\Repos\Borealis\.memdb --delete-forever`, then the daemon is started again with `MEMTRACE_NO_REPLAY=1`, set only in the environment that launches it, and it indexes the empty store on its own. Without that variable, the daemon's first index replays the git history before it computes the embeddings, and the replay holds the store lease: `find_symbol` and `find_code` fail and no embeddings exist until it ends (2026-10-26). The per-repository `memtrace reset Borealis` is not used: on a store of 28 GB its delete gave no answer within two hours (2026-10-23). See [orchestration](docs/development/orchestration.md#task-lifecycle).
- What is in the graph: the tracked `.memtraceignore` keeps Gradle Kotlin DSL scripts (`**/*.gradle.kts`), the design tokens and the prebuilt OpenSSL and Opus headers out of it, and Memtrace's default exclusions drop `**/third_party/**`, so `core/third_party/` is not in it. Use Grep and ranged reads there.
- One worktree and one branch per task, under `D:\Repos\Borealis-worktrees\<phase>-<task>`. Work only in the worktree and on the files the brief names.
- Follow the [TDD rule](docs/development/tdd.md): commit the observed failing test before the implementation.
- One phase is one integration PR, merged with **Create a merge commit** so the test-first commits stay in history.

## Inherited code

- `apps/android/` started as a subtree of [moonlight-android](https://github.com/moonlight-stream/moonlight-android) 12.2, and `core/third_party/moonlight-common-c/` is a vendored copy of moonlight-common-c. Since [ADR 0054](docs/adr/0054-declare-independence-from-moonlight.md) both are Borealis code: change them when a task needs it.
- New code is Kotlin (C++20 in `core/`); never add Java files. Sprints 12 to 14 converted all of the inherited Java to Kotlin under the rules of [ADR 0059](docs/adr/0059-convert-the-inherited-java-to-kotlin.md), so no Java is left; the places marked `(Sprint 12 backlog)` to `(Sprint 14 backlog)` were converted as is and wait for a refactor (see the [roadmap](docs/roadmap.md)). The converted Kotlin is formatted by ktfmt like any Kotlin file. Do not reformat the inherited C (`app/src/main/jni/moonlight-core/`), the inherited resources or the vendored files, so diffs stay reviewable.
- Borealis Kotlin modules live in `apps/android/borealis/` and `apps/android/build-logic/`. `apps/android/app/src/main/kotlin/` and `apps/android/app/src/main/jni/borealis/` are Borealis code too, inside the inherited `:app` module.
- Never rename the `com.limelight` namespace or `com.limelight.nvstream.jni.MoonBridge`: the JNI symbols depend on them.
- Upstream fixes arrive only by cherry-pick ([upstream cherry-picks](docs/development/upstream-sync.md)). Record every change to the vendored C sources in `core/third_party/README.md`.
- Reference sources (read-only): `D:\Repos\luminalshine` is the owner's LuminalShine fork, the reference for the host contract; refresh it with `git fetch origin --tags` and `git pull --ff-only origin main`, and never commit or push there. `D:\Repos\CandelaMoon-src\` holds the `moonlight-android` and `Artemis` checkouts used during the analysis; its `luminalshine` clone is stale.

## Writing code

- Write the least code that does the job: no speculative abstractions or options without a consumer, but never drop validation, error handling or security.
- `core/` is C++20 behind a thin C ABI (no exceptions or STL types across it). HTTP, UI and decoding stay per platform.
- Logs go through `BorealisLog`; never log PINs, tokens, keys or certificates.

## Verification

Run the checks for what you touched before finishing:

- Android: `./gradlew spotlessCheck detekt lint testDebugUnitTest :build-logic:test assembleDebug licensee koverXmlReportBorealis` from `apps/android`.
- Compose screens: also `./gradlew :borealis:designsystem:testDebugUnitTest :borealis:library:testDebugUnitTest :borealis:stream:testDebugUnitTest :borealis:settings:testDebugUnitTest -Proborazzi.test.verify=true` from `apps/android`; record references on Windows (see [building](docs/development/building.md)).
- Design tools: `python -m unittest discover -s design/accessibility` from the repository root (Python 3.11 or later, `numpy` and `Pillow`; see [building](docs/development/building.md#contrast-tool-and-the-glass-table)), for a change under `design/`, or to the glass table, the icons or the clips. CI runs it in the "Design tools" job.
- Core: `cmake --preset dev && cmake --build --preset dev && ctest --preset dev` from `core`, plus the format check CI runs, also from `core`: `find include src tests fuzz -type f \( -name '*.h' -o -name '*.hpp' -o -name '*.cpp' \) -print0 | xargs -0 clang-format --dry-run --Werror`. Use clang-format 22; CI pins the exact version in `.github/workflows/ci.yml`.

## GitHub and merges

- Pull requests are opened with the owner's own GitHub account (`magalz`); there is no bot. Subagents never push or open PRs: the orchestrator pushes the task and phase branches and opens the phase PR. Never merge: only the owner merges, after review. Passing CI or a prepared PR is not merge authorization.
- Ask before any push to `main`, visibility or settings change, store action, or message to other people.
- Commits made by agents end with a `Co-Authored-By: Claude <model> <noreply@anthropic.com>` trailer.
- Never print or commit secrets, signing keys or tokens.

Report honestly: behaviour changed, checks run and the exact revision tested, remaining limitations, and anything blocked.
