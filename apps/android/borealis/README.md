# Borealis Android modules

Borealis-owned Kotlin code lives here. `apps/android/app` is inherited code from moonlight-android 12.2 (see [ADR 0054](../../../docs/adr/0054-declare-independence-from-moonlight.md)). It is Borealis code now and is changed only when a task needs it.
New code is Kotlin under the package root `io.github.magalz.borealis`.

## Build setup

- `../build-logic` is an included build (registered with `pluginManagement { includeBuild }` in `settings.gradle`) with eight convention plugins:
  - `borealis.android.application`: applied by `app/build.gradle`. Through the AGP variant API it sets the application id (`io.github.magalz.borealis`, `.debug` suffix for debug), the labels (`Borealis` / `Borealis Debug`), minSdk 28, derives the version from git, configures release signing, the Android Lint baseline and Hilt/KSP, and applies detekt with type analysis (`BorealisDetekt`), Kover, licensee and the CycloneDX SBOM. For the native chain it also enables Prefab, passes `APP_STL=c++_shared` to ndk-build, depends on `:borealis:native` and orders that module's CMake build before the ndk-build configure step (ndk-build checks that the Prefab library file exists).
  - `borealis.android.library`: use it for every `:borealis:*` module (compileSdk 37, minSdk 28, NDK 29.0.14206865 like upstream, Java 17, Lint warnings are errors, JUnit 4 + Truth, AndroidX test runner for `androidTest`). It also applies detekt with type analysis (`BorealisDetekt`), Kover and licensee. Every Android module runs detekt, from its own `detekt` task, on the `debug` sources, the unit and instrumented tests and the test fixtures, with one config (`config/detekt/detekt.yml` under `apps/android`) and no baseline. Instrumented tests receive the borealis-core version from `core/CMakeLists.txt` as the instrumentation argument `expectedCoreVersion` (also set on `:app`).
  - `borealis.android.compose`: Jetpack Compose in a library module that already applies `borealis.android.library`: the Compose compiler plugin, the BOM-managed UI and Material 3 artifacts, and Roborazzi screenshot tests on Robolectric (references in `src/test/screenshots`).
  - `borealis.android.hilt`: the Hilt runtime and its KSP compiler (ADR 0012).
  - `borealis.android.room`: Room with its KSP compiler; the schemas are exported to the module's `schemas/` (ADR 0011).
  - `borealis.kotlin.serialization`: the kotlinx.serialization compiler plugin and the JSON runtime (ADR 0030).
  - `borealis.design.tokens`: generates the design tokens of `design/tokens.json` (task `borealisTokens`) into the Kotlin and resource sources of every variant of a library module (ADR 0044).
  - `borealis.settings`: applies Spotless to Borealis-owned paths only, and detekt to `build-logic`: ktfmt (kotlinlang style) for Kotlin and clang-format with `core/.clang-format` for `borealis/native/src/main/cpp` and `app/src/main/jni/borealis`. `clang-format` must be on `PATH`; Spotless needs its exact version, so the build reads it from `clang-format --version`. Without it the C/C++ Spotless tasks fail with "clang-format 22.x not found on PATH". Upstream Java/Groovy/C is never formatted. It also applies Kover to the root project and merges the modules' coverage there.
- Versions live in `../gradle/libs.versions.toml`.
- The `BOREALIS` markers in `settings.gradle`, `app/build.gradle` and `app/src/main/AndroidManifest.xml` stay as history. New edits to inherited code do not need them (ADR 0054).

### Version

`versionName`/`versionCode` come from the newest plain `android-vMAJOR.MINOR.PATCH` tag (pre-release tags such as `-rc1` are skipped; components above 999 fail the build; `versionCode = MAJOR * 1_000_000 + MINOR * 1_000 + PATCH`). Without a tag: `0.0.0-dev`, code 1 for debug builds; release builds fail with a message (fetch tags, CI: `fetch-depth: 0`). Commits after a tag show as `1.2.3-5-gabcdef1`.

### Release signing

Release stays unsigned unless all four values are present, either in `apps/android/keystore.properties` (git-ignored) or in the environment:

| keystore.properties | environment |
| --- | --- |
| `storeFile` | `BOREALIS_KEYSTORE_FILE` |
| `storePassword` | `BOREALIS_KEYSTORE_PASSWORD` |
| `keyAlias` | `BOREALIS_KEY_ALIAS` |
| `keyPassword` | `BOREALIS_KEY_PASSWORD` |

### Checks (from `apps/android`)

```sh
./gradlew spotlessCheck detekt lint testDebugUnitTest assembleDebug licensee
./gradlew :build-logic:test        # build-logic unit tests
./gradlew spotlessApply            # format Borealis-owned Kotlin
./gradlew :app:updateLintBaseline  # only when deliberately accepting upstream lint findings
```

Lint on `:app` uses `app/lint-baseline.xml` for the existing upstream findings; anything new fails the build, and Borealis modules have no baseline.
An opt-in pre-commit hook lives in `.githooks` at the repository root (`git config core.hooksPath .githooks`).

### Coverage, licences and SBOM

All three come from the convention plugins (`BorealisCoverage`, `BorealisLicenses`, `BorealisSbom` in `build-logic`); details in `docs/development/building.md`.

```sh
./gradlew koverXmlReportBorealis koverHtmlReportBorealis  # build/reports/kover/coverage.xml (JaCoCo format) and htmlBorealis/
./gradlew licensee                                        # part of check; fails on a licence outside the allowlist
./gradlew :app:cyclonedxDirectBom                         # app/build/reports/sbom/borealis-android.cdx.json
```

- Kover merges the debug unit-test coverage (the `debug` variant in `:borealis:*` and in `:app`) into one report at the root. Every `com.limelight.*` class counts, the inherited code (converted to Kotlin in Sprints 12 to 14, ADR 0059) included, as in [building](../../../docs/development/building.md). Only the generated Hilt/Dagger/`BuildConfig`/`R`/Compose singleton classes are excluded.
- licensee allows Apache-2.0, MIT, BSD-2/3-Clause, ISC and Zlib plus URL-only licences of Bouncy Castle and JCodec, each with a justification in `BorealisLicenses.kt`.
- `../sbom/native-components.cdx.json` is the hand-maintained SBOM of the native components in the APK; update it with every upstream sync (`docs/development/upstream-sync.md`).

## `:borealis:logging`

`BorealisLog` is the only logging entry point for Borealis code.

- Levels `VERBOSE..ERROR`, subsystem tags `LogTag` (APP, HOST, PAIR, LAUNCH, RTSP, VIDEO, PYROWAVE, INPUT, REST, CORE, UPSTREAM, COMMONC), structured fields: `BorealisLog.i(LogTag.HOST, "paired", "host" to name)` renders as `... INFO HOST paired host=name`.
- Before `BorealisLog.initialize(...)` (done in `BorealisApplication.onCreate`) records are dropped; sinks never throw into the caller.
- `Redactor` runs on every message, field and stack trace before any sink: labelled PINs, `Bearer` and `token=`/`apiToken=` values, PEM blocks and long hex/base64 values in `cert`/`key`/`signature` fields, and the pairing and launch secrets of the GameStream requests.
  - URL query values become `[REDACTED]` except for the allowlist in `Redactor.ALLOWED_QUERY_KEYS` (the same list is in `docs/policies/privacy-and-logging.md`); query keys and paths stay, `key=value` pairs in the fragment (`#...`) are treated like query pairs, and `user:password@` in a URL is redacted. The scheme is limited to 32 characters, so a long dotted or hyphenated run cannot make URL detection slow.
  - Address masking is off by default (`Redactor(maskAddresses = true)`). When on it masks IPv4 addresses whose four octets are at most 255 and that are not part of a longer dotted number (`7.1.431.0` stays), IPv6 addresses (`[IP]`) and host names (`[HOST]`): the host part of a URL and the values of keys named `host`, `hostname`, `computer` or `computerName` (also as a suffix, such as `serverHost`). A quoted value (`"Den PC"` or `'Den PC'`) is masked up to the closing quote. A host name in free text, including the upstream `LimeLog` lines, cannot be recognised and is not masked.
  - `Redactor.maskAddresses` is volatile. `BorealisLog.setMaskAddresses(Boolean)` and `BorealisLog.setMinLevel(LogLevel)` change the running configuration without a new `initialize`; they affect new lines only and do nothing before `initialize`.
  - The secret samples live in `core/tests/fixtures/redaction/secret-canaries.tsv` (columns `id`, `input`, `expected`, `secret`; synthetic values only). `RedactorSecretsTest` reads it through `borealis.fixtures.dir`, and the `:borealis:diagnostics` tests reuse it (`CanaryCorpus.kt`, used by `BundleCanaryTest`).
- `CrashHandler.install(dir, header, redactor)` takes the redactor of `BorealisLog` (created once in `BorealisApplication`), so crash reports follow "Mask addresses" too.
- The minimum level applies to every sink. `BorealisApplication` initialises it to DEBUG in debug builds and INFO in release builds (so the file sink records INFO and above there); the logcat sink keeps its own minimum.
- Sinks: `LogcatSink` (tag `Borealis.<TAG>`) and `RotatingFileSink` (`noBackupFilesDir/logs/borealis.log`, 5 files x 1 MB, one line per record, ISO-8601 UTC).
  - `RotatingFileSink` is asynchronous. `write` queues the record in a bounded queue of 1,024 records, and a writer thread appends them. When the queue is full the record is dropped and counted, and a `N records dropped` line is queued once there is room. `flush` waits for the queue to drain (2 s by default), and `flushAll` does so for every open sink. The crash handler and the diagnostic bundle call it first.
  - `LogStorage` holds the directory name (`logs`, under `noBackupFilesDir`). The two switches, `verboseLogging` and `maskAddresses`, are the `LogSwitches` interface; `SnapshotLogSwitches` in `:borealis:settings` implements it over the settings snapshot, and the diagnostic bundle reads it.
  - `NativeLogForwarder` passes the moonlight-common-c lines to `BorealisLog` under `LogTag.COMMONC`, so they are redacted. A token bucket limits them to a burst of 100 lines, refilled at 10 lines per second. The first line accepted after a suppression is preceded by `N lines suppressed`.
- `JulBridge.install()` forwards the upstream `LimeLog` (`java.util.logging`) to `BorealisLog` with tag `UPSTREAM`.
- `CrashHandler.install(dir, header)` writes a redacted `crash-<timestamp>.txt` next to the logs and delegates to the previous handler.

## `:borealis:designsystem`

The Compose design system that every screen module uses (ADR 0052, 0053). Package root `io.github.magalz.borealis.designsystem`. It applies `borealis.android.library`, `borealis.android.compose` and `borealis.design.tokens`, and depends on one other Borealis module, `:borealis:logging` (a video background that fails logs it once). `:borealis:library`, `:borealis:settings` and `:borealis:stream` depend on it.

- Tokens: `borealis.design.tokens` generates `BorealisTokens` and the token resources from `design/tokens.json` into each variant (ADR 0044). The file has two groups beside the dark palette, `high-contrast` and `colour-vision`, which become `BorealisTokens.HighContrast` and `BorealisTokens.ColourVision` (`RedGreen`, `BlueYellow`), and `Focus.OutlineThick` is the 5dp of the thicker outline. The fonts are added as resource directories from `design/fonts/<font>/res`: IBM Plex and the fonts of the Font setting (Atkinson Hyperlegible Next and Mono, Luciole, Lexend, Andika, B612 and B612 Mono; ADR 0058).
- `theme/` holds `BorealisTheme`, the colours, type, shapes, spacing and fonts, `FormFactor`, `BorealisLook` and `ReducedMotion`; the `Theme.Borealis` window theme is in `res/values/themes.xml`.
  - The fonts are bundled from `design/fonts/<font>/` (`ibm-plex`, `atkinson-next`, `atkinson-mono`, `luciole`, `lexend`, `andika` and `b612`), each folder with its licence and a README. `build.gradle.kts` lists them in `bundledFonts`.
  - `BorealisLook` is the viewer's appearance and accessibility choices (ADR 0057): `transparency` (`Transparency`: Standard, Reduced, Off), `glassTintPercent`, `glassBlurDp`, `reduceMotion` (`ReduceMotion`: FollowSystem, On, Off), `thickFocus`, `textSize` (`TextSize`: Default, Larger, Largest, which scale by 1, 1.15 and 1.3), `highContrast` and `colourVision` (`ColourVision`: Off, RedGreen, BlueYellow). Sprint 11 adds `font` (`FontChoice`), `accent` (`AccentChoice`), `backgroundIntensity` (`BackgroundIntensity`), `cardDensity` (`CardDensity`) and `textSpacing` (`TextSpacing`), per ADR 0058. `LocalBorealisLook` provides it, with the defaults for a screen that nobody gives a look. `BorealisTheme(formFactor, look)` provides the look, makes the colours with `borealisColors(look)`, and multiplies the font scale by the text size once; `TextSizeInWindow` applies it again inside a dialog or a sheet, which is a window of its own.
  - `BorealisColors` is a data class with a parameter per colour token, so a variant is a `copy`: `withSecondaryInk` (the glass), `withHighContrast` and `withColourVision`. `borealisColors(look)` gives the colours of a look, with the palette applied after high contrast.
  - `ReducedMotion` (`rememberAnimationsRemoved`, `animationsRemoved`) says whether animations are removed: the Reduce motion setting decides, and Follow system hands it to the animator scale of the system, which it watches live. `rememberPowerSaveMode` reads the battery saver and follows it live through the system broadcast.
  - `borealisSpacing(formFactor, density)` (`theme/BorealisSpacing.kt`) gives the gutter and the card padding of a form factor at a card density: the gutter does not change, and Dense cuts the card padding (ADR 0058, decision 7).
  - `BorealisDimens` holds the layout sizes that screens share: the widest content (`contentMaxWidth`), the padding and gap of a phone bar (`phoneBarPadding` and `phoneBarGap`, 4dp each), `stackedTextGap` (4dp), the reach of the focus outline (`outlineReach`, 5dp, and `thickOutlineReach`, 7dp), the padding and gap of a list of focusable rows (`listPadding`, 8dp, and `listGap`, 10dp), the width of the navigation rail (`navWidth`) and the widths of dialogs and sheets (`dialogWidth`, with `DialogWidth`, and `sheetWidth`).
- `components/` holds the shared components (buttons, dialogs, the action sheet, the host card, the cover tile, the navigation rail, text fields and the rest) and `components/settings/` the Settings rows and the two-pane layout. `BorealisPhoneBar` is the bar at the top of a phone screen: a `BorealisBackButton` (the arrow, with a 48dp touch target), the title and the actions, with `phoneBarGap` (4dp) between them on every screen, as a Material 3 top app bar leaves. `Text` (`components/Text.kt`) is the text of the app: Material's text with the word spacing of the Text spacing setting (ADR 0058, decision 4), and the detekt `ForbiddenImport` rule keeps Material's `Text` out of the code. `BackdropText` is a text that stands on the animated background, with the halo of ADR 0057 and the ink that `BackdropInk` names (ink-3 and ink-4 are ink-2 where the halo is), `BackdropKicker` is a section label in it and a heading, and `BackdropIcon` draws the same halo behind an icon. `BorealisSnackbarHost` shows snackbars as wide as their text. `StatusDot` has a shape for each state: a filled circle, a filled triangle or a hollow ring. `NavigationRail` takes a `footer` slot, and `RailFooter` (the mark, the name and the version) fills it; it takes no focus and hides when the rail is short. `BorealisTextField` is a glass field. `components/settings/` also holds `SettingsCard` (a glass card), `CollapsibleSection` (a section of the phone Settings) and `SettingsInfoRow` (a row that only reports a value, such as the Version). `borealisFocusIndication` draws the thicker outline (5dp, in ink) for Thicker focus outline and for High contrast, and the scale of a focused tile follows Reduce motion. `HostCard` is at least `size.host-card.height-tv` (176dp) high on a TV only; on a handheld or a phone it is as high as its content. The Hosts grid makes the host cards of a row share the height of the tallest of them wherever it has more than one column (`HostRows`). `focus/` holds the focus and press indication, the initial focus, the Options key (X or Menu) and `ignoreKeysHeldOnOpen` for the TV and handheld screens.
- `SettingsTwoPane` (`components/settings/`) shows the groups of Settings in a list on the left and the pane of the selected group on the right, on a TV and on a handheld (UC-009). It works like stacked tabs, and `SettingsTwoPanePanes` holds the panes:
  - Every group has a pane that is composed once and kept (`rememberComposedGroups`). `GroupPanes` stacks them: each is measured, placed and drawn in the same bounds, and only the current one is visible. A switch changes the layer properties of two panes (alpha and an offset out of the bounds) and composes, measures and records nothing else.
  - The current group is a derived state that only the layers, the list of groups and a small wrapper per pane read, so a switch recomposes neither the screen nor the rows.
  - The pane of the selected group is composed at once. The others follow after the first frame, one in each frame, nearest group first (the next, the previous and outward). A group for which `selfScrolling` is true, which is Privacy and diagnostics, brings its own content, effects and dialogs, so its pane is composed only while that group is selected.
  - A pane that is not shown cannot be touched (it is moved out of the bounds), cannot take focus from the D-pad or Tab, has no semantics node, and goes back to its top, so a group opens at its top.
  - Selection follows focus: moving D-pad focus to a group selects it at once, as a tap or OK does, so the pane follows every step of a held key. Right, and OK (Enter, the numpad Enter and gamepad A), enter the pane at its first row a frame after the group is current, in the keyboard input mode only (a tap selects the group and leaves the focus where it is), and Left from the pane returns to the selected group. `focusOnOpen` gives the selected group initial focus when the panes open, so Settings opened from the rail takes focus from the rail item.
- `background/` holds the animated background of the Library (ADR 0056, [design/backgrounds](../../../design/backgrounds/README.md)):
  - `BackgroundStyle` names the seven styles: `Off`, `AuroraCurtains` (`BackgroundStyle.Default`), `SoftGlow`, `NorthernLights`, `LightMist`, `FlowingLight` and `Starfield`. A video style carries its clip (`res/raw`) and the still of its first frame (`res/drawable-nodpi`). The names are in `strings_background.xml`, English only.
  - `BorealisBackground(style, modifier)`, internal to the module and drawn by `GlassHost`, fills its bounds. `Off` is the `page` colour. `DrawnBackground` (in `AuroraBackground.kt`) draws the two Compose styles in the draw phase, 30 times a second (24 on a TV while the glass blurs, `framesPerSecond`), in a loop of 20 s with no seam, and recomposes nothing. The loop sleeps from the time of the last frame and wakes just before the next vsync, so the rate is 30 fps at 30, 60, 90 and 120 Hz. `VideoBackground` shows a clip.
  - With Reduce motion removing the animations (Follow system follows the system) or the battery saver on, a Compose style is one still frame and a video style shows its still, with no player and no decoder.
  - `VideoBackground` puts a `TextureView` behind the screens (a `SurfaceView` until Sprint 10, which the glass cannot sample) and cuts the 16:9 clip from its centre to fill the window. The still covers the surface until the player draws its first frame. The player is made when the screen starts, plays while it is resumed, pauses with it, and is released when it stops, when the style changes and when the background leaves the composition, so a stream, which stops the Library, holds no player of the background.
  - `Media3BackgroundPlayers` is the player (`BackgroundPlayerFactory`, which a test replaces): Media3 ExoPlayer, muted, with its audio track off, looping one clip from `res/raw`. A player that fails is released, the log says so once with the clip and the name of the error, and the clip is not tried again until the style changes.
- Media3: `:borealis:designsystem` depends on `androidx.media3:media3-exoplayer` 1.11.1 (Apache-2.0, with the other Media3 modules and Guava), only for the video styles, and no other module uses it. The reason is gapless looping and hardware decoding of the clips, which the platform `MediaPlayer` loops with a hiccup. The Media3 modules hold no native code and their minSdk is 23. `androidx.lifecycle:lifecycle-runtime-compose` lets the player follow the lifecycle of the screen, and `androidx.core` registers the battery saver receiver. NOTICE lists Media3 and Guava, and ADR 0056 holds the five items of the dependency policy.
- `glass/` holds the glass of ADR 0057.
  - `GlassHost(backgroundStyle)` is the frame of a window. It draws the background once and, where the device can blur (API 31 and later) and the glass is not solid, blurs one copy of it per frame at a quarter of its size. Every glass surface samples that copy. While a dialog or a sheet is open over it, a host that blurs also blurs its whole window (24 dp), holds the background still, and the dialog draws no scrim and tints its panel (`GlassOverlays`, `OverlayGlass`).
  - `Modifier.glassSurface(shape)` draws the region of the surface from that copy, under the `surface` colour at the tint; where the glass is solid it is the `surface` colour. `GlassTextColors` gives its content the ink-3 and ink-4 that keep 4.5:1 over the background behind the surface.
  - `GlassRules` turns a look, a background and an API level into a `GlassSpec` (`glassSpec`), works out the tint floor of a background (`tintFloor`) and the text colours (`onGlass`), and says how fast the drawn background runs (`glassFrameRate`: 24 frames a second on a TV while the blur is drawn, otherwise 30).
  - `GlassContrastTable` is generated by `design/accessibility/contrast.py glass-table` from the measurement in `docs/ux/accessibility.md`: do not edit it by hand. It also holds the SHA-256 of each clip, and `GlassContrastTableClipsTest` fails when a clip changes without a new measurement.
- `adaptive/` decides the form factor (TV, Handheld or Phone) from the facts the platform reports (`FormFactorFacts`, `formFactorOf`, `rememberFormFactor`), and whether a game controller is connected. Two rules sit side by side in `ConnectedGamepads.kt`. The public `isGameController(sources, isVirtual, hasJoystickXy, keyboardType)` says whether a device is a real pad: not virtual, and a gamepad, or a joystick with the X and Y axes that is not an alphabetic keyboard. `isStreamControllerDevice(device)` says whether `Game` offers a device's key events to the controller handler before the keyboard handler; it is broader on purpose, so a TV remote's keys still reach the controller handler first. `ControllerHandler.isGameControllerDevice` delegates to it. `hasControllerJoystickAxes` applies the joystick part to an `InputDevice` for the stream's `ControllerHandler`. A wide window is a Handheld only with a game controller connected or with no touch screen, so a keyboard alone does not make a touch device a Handheld (ADR 0052, amended).
- `:app` depends on this module directly for that rule: `NativeGamepadSupport` (`app/src/main/kotlin/io/github/magalz/borealis/input/NativeGamepadSupport.kt`) calls `isGameController` with the device's sources, joystick axes and keyboard type to decide whether Android already handles a USB pad, so that the USB driver leaves it alone. `BorealisAndroidApplicationPlugin` adds the dependency to `:app`.
- `testFixtures` (a test fixtures artifact, never packaged into an APK) holds `testing/InputDevices.kt` (fake input devices with their sources, joystick axes and keyboard type, and their connection to the input manager) and `testing/WindowSettling.kt` (`ComposeTestRule.settleWindows()`, which lets every window of a Robolectric test settle to its final size before a screenshot). Sprint 10 added `FakeInputModeManager` (an input mode that a test sets), `OutlineProbe` (`colourOutside`: the colour just outside an edge of a node, for the focus outline), `SnackbarProbe` (`assertSnackbarIsAsWideAsItsText`), `TextFit` (`assertNoClippedText`), `TextReading` (`textColor`, `textLayout`), `SystemAnimations` (`systemAnimationScale`, `noAnimations`), `Frames` (`frame`, `rootFrame`, `recompositions`), `Halos` (`assertHalo`, `assertNoHalo`), `ScreenBackdrop` (`OnPage`, `OverMarker`), and for TalkBack `ScreenReader` (`readingOrder`, `headings`, `paneTitles`) and `AccessibilityChecks` (`assertAccessible` and `AcceptedFinding`). `AccessibilityChecks` runs Google's Accessibility Test Framework through `io.github.takahirom.roborazzi:roborazzi-accessibility-check`, a `testFixturesApi` dependency that is never on the release classpath (ADR 0057); each accepted finding needs a reason (see `docs/ux/accessibility.md`). The `:borealis:library`, `:borealis:settings` and `:borealis:stream` tests use them through `testFixtures(project(":borealis:designsystem"))`, and so do the `:app` tests, through `BorealisAndroidApplicationPlugin`.

## `:borealis:settings`

The Compose module for Settings, Privacy and diagnostics, the Audit trail viewer and Send to phone (Sprint 6). Package `io.github.magalz.borealis.settings`; it depends on `:borealis:designsystem`, `:borealis:diagnostics` and `:borealis:logging`.

- `ui/` holds the Settings screen (`SettingsRoute`, `SettingsScreen`) and its ViewModel. The groups and rows follow [UC-009](../../../docs/use-cases/0009-change-settings.md). There are eleven groups, in this order (`SettingsGroupId`): Stream, Video, Input, Gamepad, On-screen controls, Audio, Advanced, Appearance, Accessibility, Privacy and diagnostics, and About (ten on a device with no touch screen, which has no On-screen controls). On a phone each group is a `CollapsibleSection`, all collapsed at first, and the open ones survive a recreation and a trip to Privacy and diagnostics. On a TV or handheld, `SettingsScreen` puts them in a `SettingsTwoPane` with `focusOnOpen`, and Privacy and diagnostics is its self-scrolling group. `catalog/` lists the settings, and `options/` and `device/` decide which rows and values a device offers from its facts.
- `RowValue` (`ui/SettingsItemRows.kt`) is what one row draws of the `SettingsUiState`: whether it is checked, the key of the chosen entry, the entries of the Resolution and Frame rate lists, a slider's number and whether Bitrate is automatic. `SettingsUiState.rowValue(item)` builds it. A row takes only its `RowValue` and is skipped unless that changes, so a change of one setting recomposes the row of that setting and not every row of every pane.
- `appearance/` holds `BackgroundChoices`, the seven background styles of the Background row of the Appearance group, which has seven rows (Font, Accent colour, Background, Background intensity, Card density, Glass tint and Glass blur). The styles are, in the order of the row: Aurora curtains (the default), Soft glow, Northern lights, Light mist, Flowing light, Starfield and Off. Each has a stable id (`aurora_curtains`, `soft_glow`, `northern_lights`, `light_mist`, `flowing_light`, `starfield` and `off`), never an ordinal. `BackgroundChoices.all` is a `LookList<BackgroundStyle>`: a setting with its choices, read with `valueIn(snapshot)`, which gives the default style for an id that no style has. `BorealisLooks.kt` holds `LookLists`, the lists of the Accessibility and glass rows with their stable ids, and `borealisLook(snapshot)`, which maps the settings to a `BorealisLook`. `rememberLooks(settings)` returns `Looks(look, background)`, which `LibraryActivity` reads once, as derived state, so a change of another setting recomposes nothing. The stream reads the same mapping once, when it starts (`StreamSessionFactory.look` in `:app`).
- `privacy/` holds the Privacy and diagnostics pane and screen: the export, the "Diagnostics saved" dialog and "Erase audit trail". `audit/` holds the Audit trail viewer. `transfer/` holds the Send to phone dialog, which runs over `TransferController` (UC-006).
- `repository/` and `store/` hold the settings storage (ADR 0055). `SettingsRepository` is the only writer from Kotlin. It exposes a snapshot as a state flow. `StoreSettingsRepository` keeps the stream settings in the default SharedPreferences file under their current keys, so the inherited readers do not change.

## `:borealis:diagnostics`

The local audit trail and the diagnostic bundle (ADR 0050). Package `io.github.magalz.borealis.diagnostics`; it depends on `:borealis:logging`. The Privacy and diagnostics pane of `:borealis:settings` uses its public APIs (`DiagnosticsExporter`, `TransferSession`, `AuditTrail`). The policy is in [privacy-and-logging.md](../../../docs/policies/privacy-and-logging.md).

### Audit trail

- `BorealisAudit` in `:borealis:logging` is the facade that the host code calls. Until a sink is installed, events are dropped. It redacts each event before the sink receives it.
- `AuditStore` queues each event, and one writer coroutine stores them in a Room database at `noBackupFilesDir/audit.db` (table `audit_events`). The queue holds 256 events and drops the oldest one when it is full.
- Retention keeps the newest 2,000 entries and nothing older than 90 days. Deduplication applies only to `CERTIFICATE_CHANGED` and `TLS_FAILURE`, within 24 hours (`AuditDeduplicator`).
- `AuditSection` writes the trail to `audit.jsonl` in the bundle: one JSON object per line, oldest first, UTC timestamps. It redacts each entry again with the current "Mask addresses" setting.
- `AuditStore.erase()` deletes the stored entries; the Privacy pane asks for confirmation first. Bundles that were exported before are not changed.

### Diagnostic bundle

- `DiagnosticsExporter` runs `ExportFlow`, which builds the zip in `cacheDir/diagnostics`. The file name is `borealis-diagnostics-<timestamp>.zip`. Only the newest bundle is kept.
- Layout: `manifest.json`, `decoders.json`, one file per section (`audit.jsonl`) and the log files under `logs/`.
- The uncompressed content stays within 16 MiB. Sections are written first. The log files get the rest, newest first. The first file that does not fit keeps its newest lines, and the older files are dropped. `manifest.json` lists what was cut.
- Each section redacts its own content, so a JSON line is not redacted twice. The log lines are re-redacted line by line with the current setting, so "Mask addresses" also applies to lines written before it was turned on.
- `flushLogs` runs before the log files are read, so queued lines reach the files first.
- `DecoderReport` builds `decoders.json`: the H.264, HEVC and AV1 decoders with their profile names, and the HDR types of the default display.
- The zip is shared through a `FileProvider` with the authority `${applicationId}.diagnostics.fileprovider` (paths in `borealis_diagnostics_paths.xml`). On a phone or tablet the share sheet opens when an app can receive the zip. On a TV (`UI_MODE_TYPE_TELEVISION` or the leanback feature) it never opens by itself, because apps such as VLC accept any `ACTION_SEND` and would take the file: the bundle is saved and the "Diagnostics saved" dialog shows where. A phone with no receiver does the same. The save goes through a `BundleStore`: on API 29 and later `DownloadsBundleStore` inserts the zip into `MediaStore.Downloads` (MIME `application/zip`, `IS_PENDING` while it is written, no storage permission), so the file is at `/sdcard/Download/<name>` and the dialog shows `Download/<name>` and `adb pull /sdcard/Download/<name>`. On API 28 `AppFilesBundleStore` copies it to `getExternalFilesDir("diagnostics")` and the dialog shows that path and its `adb pull` command. Only the newest bundle this app saved is kept (MediaStore shows an app only its own entries). The dialog text is focusable and scrolls, and Close has the focus. On a phone or tablet an optional "Share…" button opens the chooser with the `FileProvider` URI; on a TV the dialog has no such button, because the only receiver there is usually a video player.

### Send to phone

`transfer/` hands the bundle to a phone on the same network (ADR 0051, UC-006).

- `TransferSession` is the public entry: a singleton that serves one file once and reports a `StateFlow<TransferState>` (`Idle`, `NoNetwork`, `Waiting` with the link, its QR code and the countdown, `Downloaded`, `Expired`, `Stopped`, `Failed`). `start(file)` closes an earlier link first and `stop()` closes the current one at once.
- `OneShotFileServer` serves the zip once over plain HTTP: the zip is at `/<token>/<file name>`, and `GET /<token>` is a landing page that does not use up the download. The link is `http://<address>:<port>/<token>` (a 128-bit random token). It stops at the first complete download, after 5 minutes or on `stop()`; a watchdog thread enforces the 5 minutes. `TransferHttp` reads the request line and holds the few statuses it answers with.
- `TransferQr` draws the QR code of the link (ZXing, error correction M). `LocalNetwork` finds the private IPv4 address of the active Wi-Fi or Ethernet network; with none (mobile data, no connection) no link starts and the state is `NoNetwork`.

### Hilt

- `BundleModule` declares `@Multibinds Set<DiagnosticSection>`, so the bundle works with no contributor. A module adds a section with `@Provides @IntoSet` or `@Binds @IntoSet` (`AuditModule` uses `@Provides @IntoSet` for `AuditSection`).

## `:borealis:native`

The Android side of the C++ core (ADR 0010, 0043). Package `io.github.magalz.borealis.nativecore`.

```text
borealis/native/
  build.gradle.kts                CMake + Prefab publishing
  src/main/cpp/CMakeLists.txt     add_subdirectory(<repo>/core), builds libborealis_jni.so
  src/main/cpp/borealis_jni.cpp   hand-written JNI for CoreJni
  src/main/kotlin/                BorealisCore, NativeLibrary, CoreJni, HostRules, HostMarshalling
app/src/main/jni/borealis/        Android.mk + borealis_bridge.c (ndk-build side)
app/src/main/kotlin/.../NativeBridge.kt
```

- `BorealisCore.version()` returns the core version (`borealis_core_version()`), or `null` when the native library is unavailable.
- `HostRules` / `NativeHostRules` expose the four LuminalShine host rules of `core/include/borealis/host.h`: `parseCaps(appVersion, codecMask)` (family, version, HEVC, HEVC Main10, AV1, AV1 Main10, 4:4:4 and the PyroWave profiles), `decideLaunch(verb, status, message, attemptsInCategory)` (the launch/resume retry decision, including `RESOLVE_CONFLICT` for a 400 "An app is already running" on `/launch`), `classifyPairing(status, message)` (`PairAction` and `PairCategory` of a `/pair` error) and `launchFps(isGfe, launchFps, streamFps)`. Every call returns `null` when the native library is unavailable or the core rejects the input, so callers fall back to the upstream behaviour; `HostRules` is the interface its consumers take so JVM tests can use a fake.
- The JNI carries only primitives: UTF-8 `ByteArray` inputs (`null` array = NULL pointer with length 0, an empty array = empty string) and `IntArray` results whose first element is the `BOREALIS_*` status (caps: `[status, family, v0..v3, codec_flags, pyrowave_profiles]`; decision: `[status, action, delay_ms, category, max_attempts]`; pairing decision: `[status, action, category]`). `HostMarshalling` holds the pure Kotlin side and is unit-tested on the JVM:
  - the host message is cut to 256 UTF-8 bytes without splitting a character (the core matches ASCII substrings only);
  - an `appversion` over 64 bytes is not truncated: the call returns `null` and logs a WARN on `CORE` with the byte count only;
  - `codecMask` keeps its raw 32-bit pattern (`0x80000000` is `Int.MIN_VALUE`); a negative `attemptsInCategory` is clamped to `Int.MAX_VALUE` because the core reads it as `uint32` (a huge count, hence `FAIL`);
  - a non-OK status, a malformed array or an unknown enum value decodes to `null` with a WARN on `CORE` (status or value only, never input content). `HostCaps.version` is always four ints, all 0 for `HostFamily.UNKNOWN`.
- `borealis_jni.cpp` copies the inputs into bounded stack buffers (`GetByteArrayRegion` after a length check), never throws and clears any pending Java exception before returning `null`.
- `GoldenVectorsInstrumentedTest` replays `core/tests/fixtures/vectors/*.tsv` (host caps, launch decisions, pairing classification and frame rate) (added as androidTest assets in `build.gradle.kts`) through `NativeHostRules`, so the C ABI and the Kotlin binding cannot drift apart. It needs a device or emulator (`connectedDebugAndroidTest`); `assembleDebugAndroidTest` only compiles it.
- `NativeLibrary(name)` loads a JNI library once and never throws: a missing library or symbol is logged once through `BorealisLog` (tag `CORE`, fields `library`, `operation`) and calls return `null`. Its `loader` parameter is the seam for JVM tests, which therefore never need a real `.so`.
- `BorealisApplication.onCreate` calls `BorealisCore.logStartup(NativeBridge.coreVersion())`: one INFO line `... CORE borealis-core loaded core=0.1.0`, plus a WARN when the ndk-build bridge reports another version or either library is unavailable.

### Two native build systems

AGP allows one `externalNativeBuild` per module, and upstream `:app` uses ndk-build. So:

1. `:borealis:native` builds `core/` with CMake (`add_subdirectory`, tests off) into `libborealis_core.so` and its own `libborealis_jni.so` (Kotlin `BorealisCore`).
2. `prefabPublishing` + `prefab { create("borealis_core") }` publish `libborealis_core.so` and `core/include` as a Prefab package. The package name is the Gradle project name, so it is `native`.
3. `:app` has `buildFeatures.prefab = true`. The Borealis-owned `jni/borealis/Android.mk` (picked up by upstream's `include $(call all-subdir-makefiles)`, so no upstream makefile changes) builds `libborealis_bridge.so` with `LOCAL_SHARED_LIBRARIES := borealis_core` and `$(call import-module,prefab/native)`. `NativeBridge.coreVersion()` calls it, proving that moonlight-core-side ndk-build code can link the core.

Upstream native code (`Application.mk`) is untouched, and moonlight-common-c is vendored in `core/third_party/`, and its changes from upstream are listed in `core/third_party/README.md`; the only upstream-facing native settings are `APP_STL=c++_shared` (passed from the convention plugin) and the Prefab flag.

### Static or shared, and the STL

The core is published as a shared library (`BUILD_SHARED_LIBS=ON` inside the module's CMake) built with `ANDROID_STL=c++_shared`, and the app's ndk-build uses `APP_STL=c++_shared`.

- Prefab rejects the alternatives for a shared core: a shared library with a statically linked libc++ "cannot be used with any library using the STL", and consumers that declare no STL are refused for libraries that need libc++ (AGP reports `CXX1211`/`CXX1213`). ndk-build without `APP_STL` counts as "no STL".
- One STL per app: the JNI library and the core (and later the bridge, once it uses C++) share one `libc++_shared.so`, which is packaged next to them. A static core (not tried) would instead be linked, with its STL, into every consumer and duplicate both.
- Only the C ABI of `core.h` is exported (hidden visibility, no STL types across it), so the STL choice never leaks to callers. Upstream code is plain C: `libmoonlight-core.so` does not depend on libc++, and the C bridge does not either.
- Both libraries are 16 KB page aligned on arm64-v8a and x86_64 (NDK 29 default); the 32-bit ABIs use 4 KB like upstream.

### Verifying without a device

```sh
./gradlew assembleDebug :borealis:native:assembleDebugAndroidTest :app:assembleDebugAndroidTest
```

The APK has `lib/<abi>/libborealis_core.so`, `libborealis_jni.so`, `libborealis_bridge.so` and `libc++_shared.so` for armeabi-v7a, arm64-v8a, x86 and x86_64. `llvm-nm -D` shows `borealis_core_version` defined in the core library and undefined (imported) in the JNI and bridge libraries. On a device or emulator run `./gradlew :borealis:native:connectedDebugAndroidTest :app:connectedDebugAndroidTest`; both assert that the packaged libraries report the version declared in `core/CMakeLists.txt`.

## `:borealis:host`

Every LuminalShine compatibility rule on the Android side lives here (the host contract in `docs/host-contract` is the reference). Package root `io.github.magalz.borealis.host`; the module depends on `:borealis:logging` and `:borealis:native`, and `:app` and `:borealis:stream` depend on it.

| Package | Content |
| --- | --- |
| `host.pairing` | PIN and unpair hints, best-effort `/unpair`, messages and the single restart for host pairing errors |
| `host.launch` | App launch and resume requests (retries, cancellation, the running-app conflict) |
| `host.caps` | Host capabilities derived from `/serverinfo` |
| `host.video` | Stream startup: first-frame message and watchdog, no-video error hints |
| `host.failure` | Why a stream start failed or a stream ended: the classified failure for the connection error screen |

`LaunchAudit` and `SessionAudit` in `host.launch` and `PairingAudit` and `TlsAudit` in `host.pairing` record the audit events of ADR 0050 through `BorealisAudit`: status codes, categories, ids and negotiated values, and a short fingerprint prefix for a certificate, never a host message, an app name or a PIN.

### `host.pairing`

LuminalShine does not route `/unpair`, and the user types the PIN and the device name in the host Web UI (contract sections 4.1 and 10.2, requirement 4).

- `BestEffortUnpair.unpair(client, url)`: sends `/unpair` with `Connection: close`, because LuminalShine writes stray bytes after its response on that connection, reads at most 16 KiB of body and returns true only when the XML root has `status_code="200"`. An I/O error, a non-2xx status or an unreadable body is false instead of an exception (it blocks on the network, so call it off the main thread) and the outcome is logged on `LogTag.PAIR` without the URL. `NvHTTP.unpair()` delegates to it and returns the result; `PairingManager` ignores it. The Library's removal of a host (`ComputerHostRepository`) calls it best effort, and the host is removed on this device either way.
- `PairingHints`: `webUiUrl(address, httpPort)` is `https://<host>:<httpPort + 1>` (IPv6 bracketed once, zone id percent-encoded per RFC 6874, null for a port outside 1..65534 or an unusable address); `suggestedDeviceName(model)` removes `xbox` and `webos` in any case and falls back to `Borealis`. The Library pairing (`NvPairingService`) uses both.

- `PairingErrors.describe(context, error, fallback, restarted)` turns the host answer behind a failed pairing step into a `PairingFailure(message, restart)`. `HostRules.classifyPairing` decides: for a session the host dropped (400 `Out of order call to getservercert`, 400 `Invalid uniqueid`, 400 `Pairing exchange invalidated`, 410 `Host pairing state was reset`) the message is "The host had an unfinished pairing attempt and has cleared it. Enter the new PIN." and `restart` is true, once: when `restarted` is already true the same error is a plain failure ("The host cleared the pairing attempt again..."). The errors of a session the host still holds (409 in progress, 409 identity mismatch which means another device is pairing, 503 too many pending) and the specific failures (403 peer mismatch, 409 superseded) get their own text and never restart. Anything else, a non-host exception and an unavailable core keep the upstream text. The log line carries the status, category and action only, never the host text or a PIN.
- The Library pairing (`NvPairingService` in `:app`) calls it in its failure path, with the `restarted` flag. When `restart` is true the pairing runs once more, so one new PIN prompt appears. The 12.2 `PcView.doPair` that did this before is removed with `PcView` (Sprint 5).
- OkHttp: the pairing clients keep OkHttp's default `retryOnConnectionFailure`. The held phase 1 request has no read timeout, so a timeout cannot resend it; only a connection-level failure before the response can make OkHttp send it once more, and the host answers an identical retry by superseding the first request (409 `Pairing request superseded by retry`) instead of failing. No evidence of a problem, so it is left as it is.

### `host.launch`

LuminalShine answers `/launch` and `/resume` with 409 and 503 errors that ask the client to retry (another launch is pending, the previous stream is still restoring the display, the GPU or display stack is not ready; host contract 7.5), and rebuilds its virtual display when the `/launch` and RTSP modes differ (7.4). Upstream Moonlight never retries and, with frame pacing "cap FPS", sends two different rates.

- `LaunchRetryRunner` runs one request through an attempt function. A `HostError(code, message)` that the hook's extractor recognises goes to `HostRules.decideLaunch`. The runner counts retries per category (the core is stateless, so a first call learns the category and a second one carries the count), waits the decided delay in slices of at most 250 ms while polling the cancel supplier, and gives up when the next wait would pass the total budget (`DEFAULT_BUDGET_MS`, 60 s). It reports `SUCCEEDED`, `FAILED` (the host answered 200 but did not start the app), `FALLBACK_TO_LAUNCH` (a `/resume` answered 503 "No running app to resume") `CONFLICT` (a `/launch` answered 400 "An app is already running on this host", only while the caller's `conflictAllowed` supplier says that it may still be resolved; otherwise the error is rethrown), or `CANCELLED`. A cancellation, including an interrupted wait, returns without throwing.
- Everything else is rethrown as the original instance, so upstream's 470/525/599 handling and `stageFailed` mapping keep working: a throwable the extractor does not recognise, a FAIL decision, an exhausted category or budget. When `HostRules` returns null (native library not loaded) the original exception is rethrown too, with one ERROR on `LogTag.LAUNCH`. Retries log the category, the attempt and the delay, never the host message. The runner has no HTTP access and never calls `/cancel`, which would also cancel another client's pending launch.
- `LaunchRetries.run(LaunchRequest, LaunchAttempt, LaunchHooks)` is the entry point that `NvConnection` calls: `LaunchRequest` is the GFE flag, the verb string and the host (for the audit only), `LaunchAttempt` is one `/launch` or `/resume` request, and `LaunchHooks` holds the `HostErrorExtractor`, the cancel `BooleanSupplier`, the `RetryProgress` callback (category ordinal, attempt, retries allowed, delay) and the `conflictAllowed` supplier. GFE hosts (`isNvidiaServerSoftware`) bypass the runner, as upstream. Everything else is mapped to the runner.
- `LaunchConflicts` (one per `NvConnection`) resolves a `CONFLICT` with the user, at most once per launch (`isOpen()` is the `conflictAllowed` supplier, so a second 400 after Join or Quit fails like any other error and the chain resolver, quit, launch, 400 cannot loop). `resolve(reader, names, requested, actions, host)` takes the `RequestedApp` (id and name) and the `ConflictActions` (the `ConflictPrompt`, the relaunch, the join and the quit and relaunch that the connection supplies), and re-reads `currentgame` from `/serverinfo` through the reader for up to 3 s (every second, waiting in 250 ms slices, honouring the cancel flag): `0` launches again once through the normal path; otherwise it asks through `ConflictPrompt` (running app id and name when the app list tells it, requested app id and name; the dialog says when they are the same app) and waits for the `ConflictAnswer` in 250 ms slices. Join is `/resume` of the running app id through the existing retry path (a `/resume` that finds nothing to resume launches instead); Quit and relaunch is the upstream `quitAndLaunch`; Cancel, the dialog closing, Back, `onStop`, `cancelLaunch()` and an interrupted wait end the launch quietly, with no `stageFailed` dialog. `ConflictAnswer.choose` returns whether the choice won. It never calls `/cancel` itself and logs the choice only, never an app name.
- `LaunchProgressText.format` builds the text of the Starting screen in English from `strings_launch.xml`, for example "Another device is starting a stream on this host. Retrying in 2 s (retry 2 of 4)." The number counts retries, not requests: the first request is not a retry. There is one text per retried category plus a generic one.
- `LaunchFrameRate.forLaunch(isGfe, launchFps, streamFps)` is the `mode=` frame rate of `/launch`: the stream rate announced over RTSP for non-GFE hosts, and the upstream rule (`isGfe && launchFps > 60 ? 0 : launchFps`) for GFE and whenever `HostRules.launchFps` returns null.
- `ResumeCollisions` (one per connection) lets a second device in while LuminalShine is still building another device's virtual display (host contract 7.3). It reads `/serverinfo` through `ServerInfoRetry` (a read timeout is retried, 3 attempts within 25 s), waits 3 s before `/resume` when `/serverinfo` showed that the host was busy, and restarts the whole start once when RTSP fails right after an accepted `/resume` (`HeldStageFailures` in `:app` holds that failure back). When that fails too, or the restart finds another app running (a restart never quits it), the error says that another device was starting its stream instead of blaming the firewall.

### `host.caps`

- `HostInfoReader.read(hostId, appVersion, codecMask, httpsPort, httpPort)` builds a `BorealisHostInfo` (the `HostCaps` of `HostRules.parseCaps` plus both ports) from the raw `appversion` and `ServerCodecModeSupport` texts of `/serverinfo`. A missing or unreadable mask counts as 0 (the low 32 bits of a larger number are kept, so `0x80000000` arrives as `2147483648`), so a malformed host cannot break the poll. It returns null when the rules are unavailable or reject the version text.
- `/serverinfo` is polled all the time, so the reader logs one INFO on `LogTag.HOST` per host, and only when the information of that host changes. `NativeHostRules.parseCaps` itself still logs a WARN on every call for an `appversion` over 64 bytes.
- `NvHTTP.getComputerDetails` stores the result in the transient `ComputerDetails.borealis`, which `update()` copies. `ComputerHostRepository.details` returns the host details text to the Library: `HostDetailsText` lists what the client knows of the host in plain lines (name, status, address, other addresses, pairing, MAC address for wake and running app; an unknown value leaves its line out, except the status, which then reads "Checking…"; an address shows its port only when it is not the default HTTP port), and `HostInfoText.appendTo` appends a localized block after a blank line with the host software and version, HEVC, AV1, 10-bit and 4:4:4, the PyroWave profiles or "off", and the HTTP and HTTPS ports.

### `host.video`

LuminalShine can need about 18 s after the client attaches to send the first frame (contract section 10.1); upstream Moonlight dismisses the spinner at `connectionStarted`, long before that.

- `StreamStartupGuard(terminate)` is what `Game` holds. `Game` passes only the termination callback, so its hooks hold no logic. It runs the `FirstFrameWatchdog` from `connectionStarted` until the first rendered frame. During that wait the user sees the Starting screen of `:borealis:stream`, which has its own "Preparing the display" step.
- `FirstFrameWatchdog` (states IDLE, ARMED, SATISFIED, FIRED, CANCELLED; one terminal state per stream) ends the stream with `ML_ERROR_NO_VIDEO_FRAME` if no frame is rendered 45 s after `connectionStarted`, above the about 35 s worst case of the patched moonlight-common-c deadlines. The termination runs off the main thread because `Game.connectionTerminated` does network I/O first. The watchdog is cancelled on stop, `onStop`, `onDestroy` and termination.
- `FirstFrameSignal` is raised by `MediaCodecDecoderRenderer` at the first output buffer released for rendering (Choreographer and renderer-thread paths); after that it costs one volatile read per frame.
- `StreamErrorHints.withHint` appends a LuminalShine hint to the -100 (no video traffic) and -101 (no complete frame) messages; the blocked-port message is left unchanged.
- `HevcSpsMonitor` (fed by `MediaCodecDecoderRenderer` with each HEVC SPS) logs the profile, chroma format and bit depth on `LogTag.VIDEO` when they change, and warns when the stream is 10-bit and the decoder does not declare Main10 or when 4:4:4 is downgraded to 4:2:0; `HevcSps` reads the SPS (emulation prevention, sub-layers, bounded Exp-Golomb) without ever throwing, so decoding is unaffected.
- `HdrRestartReuse` keeps the IDR frame that `MediaCodecDecoderRenderer` is submitting when the decoder restarts to apply HDR metadata. The restart clears the stored VPS, SPS and PPS, so the renderer takes a `snapshot` of them while a restart is pending and puts them back with `restoreForRetry`, and the same IDR goes to the restarted decoder. Without it the frame is dropped and a new IDR is requested from the host, which costs seconds.

### `host.failure`

The connection error screen of `:borealis:stream` shows what this package classified. `StreamFailures` in `:app` gathers the facts, and the strings are in `res/values/strings_failure.xml`.

- `FailureCauses.of(error, hostHttpCode)` turns what a failed start threw into a `CauseKind` (`NONE`, `CERT_MISMATCH`, `UNREACHABLE`, `TIMEOUT`, `HTTP`). A timeout while the TCP connection is made is `UNREACHABLE` (nobody answered: the PC is off or asleep), and one after it is `TIMEOUT` (the host is there but busy). `retriesExhausted` says that the 409 and 503 launch retries ran out.
- `StartSteps` holds the words that name a step of the HTTP start in the raw code of a failure (`serverinfo`, `launch`, `resume`, `quit`). They are English, never change and are never the name of the app.
- `StreamFailureClassifier.classify(facts, text, portFlagsText)` turns the `FailureFacts` (stage, error code, port flags, cause, HTTP status and a few flags) into a `StreamFailure(kind, rawCode, portHint)`. The `FailureKind` is `CERTIFICATE_CHANGED`, `HOST_BUSY` (another device was starting its stream, the retries ran out, or a read timed out after connecting), `HOST_OFFLINE` (nothing answered the TCP connection, so the screen offers Wake PC), `STOPPED` (the stream reached the first frame and then ended with a generic failure) or `GENERIC`; the first rule that matches wins. The port hint goes with `GENERIC`, `STOPPED` and `HOST_OFFLINE` failures that have port flags, except when the PC answered but its reply could not be read.

User-facing strings of the module stay in the module, one file per area. The app is English-only until a translation sprint: the inherited translations and the Brazilian Portuguese files were removed, and the locale config lists `en` only. Files: `res/values/strings_pairing.xml`, `strings_stream.xml`, `strings_launch.xml` and `strings_failure.xml`.

### Fixtures in unit tests

`borealis.android.library` gives every unit-test task of a `:borealis:*` module, and `borealis.android.application` gives the same to the application module, the system property `borealis.fixtures.dir`, the absolute path of `core/tests/fixtures` (layout, provenance and scrubbing rules in its `README.md`). The directory is a test input, so changing a fixture re-runs the tests. In `:borealis:host` the test helper `Fixtures` resolves a fixture by relative path (`Fixtures.text("luminalshine/26.09.1/serverinfo-http.xml")`) and fails with a clear message when the property or the file is missing. `FixturePolicyTest` enforces the public-repository rules on every file under `luminalshine/`: scrubbed host name, `uniqueid`, MAC and addresses, and a `device` or `source` provenance row for each file.

## `:borealis:library`

The Compose Library, the launcher of the app (ADR 0052). Package root `io.github.magalz.borealis.library`. It depends on `:borealis:designsystem`, `:borealis:logging` and `:borealis:settings` (the Settings graph is one of its destinations); its tests also use `:borealis:diagnostics`, because the Hilt test components aggregate the Settings graph's modules, and the designsystem test fixtures. It does not depend on `:borealis:host`: the screens see only the interfaces of `domain/`, and `:app` implements them and binds them through Hilt (`LibraryAdapterModule`).

- `hosts/`, `apps/`, `addhost/` and `pairing/` hold the screens, each with its route, screen, UI state and ViewModel: Hosts (the host cards and their dialogs), Apps (with the App actions sheet), Add host and Pairing (the PIN, entered in the host's Web UI). Hosts keeps the key of the card that last had the focus, or that a tap or Continue chose (`FocusedCard`, `HostsFocusRestore.kt`), in its own saved state, so that Back from Apps, a rotation and Cancel on Add host return to it by host and not by place; a host that is gone falls back to the first card.
- `domain/` holds the contracts: `HostRepository`, `AppRepository`, `PairingService`, `StreamLauncher`, `LegacyBridge` and `HostShortcuts`, with their data types and `HostAddressParser`. `:app` implements them (`ComputerHostRepository`, `ComputerAppRepository`, `NvPairingService`, `GameStreamLauncher`, `UpstreamLegacyBridge` and `UpstreamHostShortcuts`).
- `shell/` holds `LibraryActivity`, the launcher activity, whose manifest entry is declared here; `LibraryNavHost`, the navigation between the screens (Hosts, Add host, Pairing, Apps and the Settings graph of `:borealis:settings`); and `LibraryRail` with `LibraryScaffold`, the frame of the screens: on a TV or handheld the content has the navigation rail beside it, a glass rail that ends in a footer with the mark, the name and the version (`RailFooter`, read from the place About reads them). The frame is a `GlassHost` of `:borealis:designsystem`: `GlassHost` draws the background (`BorealisBackground`, which is internal to that module) once, behind the rail and the content, on every form factor, and the glass surfaces of the screens show it blurred. `LibraryActivity` reads `rememberLooks(settings)` once, which gives the look and the background (`Looks`), and passes both through `LibraryNavHost` to the frame. So a change of the Appearance setting shows behind Settings at once, and the glass and the Accessibility settings change the Library at once. `QuitNotice` is the one-shot notice that a Quit in the stream leaves, and `ShowQuitNotice` shows it as "App quit." in the snackbar host of the shell (`BorealisSnackbarHost`) once, while a Library is started; it is dropped when no Library is there. The screens are transparent: none paints its own page, and the rail is glass too (the `chrome` colour where the glass is solid). `FadingNavHost` fades the next screen in over 150 ms and removes the screen that is left at once (a `snap()` exit), because a fade-out beside the fade-in would show two transparent screens one over the other. The stream is another activity, so the background is never in a stream.
- `LibraryLaunchRequest` is what the stream activity or a shortcut asks the Library to show or do (the host list, the apps of a host, launch an app, pair again, Privacy), carried as intent extras.
- The shortcuts are `HostShortcuts` (the contract, here) and its implementation, `ShortcutTrampoline` and `ShortcutIntentParser` (in `:app`, described below). Strings are in `res/values/strings_*.xml`, English only.

## Library and launcher shortcuts (`:app`)

- The Library is the launcher. `LibraryActivity` (`:borealis:library`) shows the Compose screens: Hosts, Add host, Pairing, Apps and App actions. Sprint 5 removed `PcView` and `AppView`, with the 12.2 grids and the code that only they used.
- `ShortcutTrampoline` (`app/src/main/kotlin/com/limelight/ShortcutTrampoline.kt`) is the entry of every launcher shortcut. It keeps the 12.2 component name and extras (`UUID`, `Name`, `AppId`, `AppName`, `HDR`), so the shortcuts that 12.2 pinned keep working. `ShortcutIntentParser` maps the extras to a `LibraryLaunchRequest`: a PC shortcut opens the apps of that PC, an app shortcut launches that app, and a shortcut that names no PC (the name-only shortcuts of old releases) opens the host list. The trampoline starts `LibraryActivity` with clear-top and single-top, then finishes.
- A launch request starts the app as a tap does. When another app is running, it opens the conflict sheet instead.
- Opening a host publishes or updates its launcher shortcut (`HostShortcuts.reportHostOpened`). On a phone, "Add to home screen" on an app pins a shortcut for that app (`HostShortcuts.pinApp`). TVs do not offer it. Pinned app shortcuts use the generic PC icon.
- Not done: the TV channel "add to home screen" prompt after pairing.

## `:borealis:stream`

The stream chrome: the screens and state that sit over the stream in `Game`. Package root `io.github.magalz.borealis.stream`. It holds the starting screen, the conflict dialog, the connection error screen, the in-game menu with its pull handle and first-run hint, the Borealis keyboard and the performance overlay. It depends on `:borealis:designsystem` and `:borealis:logging`, and exposes `:borealis:host`, `:borealis:native` and `androidx.activity` to its callers.

- Contracts: `StreamUiState` with the phases `Starting`, `Conflict`, `Failed`, `Quitting` (a quit is pending and the host has already ended the stream: the screen is quiet, and a quit that fails turns it into `Failed`) and `Streaming`; `StreamActions` (what the activity does for the chrome) and `StreamIntents` (what the screens call); `PerfSnapshot` and its sink. `StreamSession` implements the intents and takes events from any thread into one `StateFlow`. Once a failure is shown, late events do not change it.
- `ui/`: `StartingScreen`, `ConflictDialog`, `ConnectionErrorScreen` (with `error/`), `QuittingScreen`, `menu/` (`InGameMenu`, `MenuHandle`, `QuitConfirmation`), `StreamKeyboard` with `keyboard/` (layout and latch), `overlay/` (`PerfOverlay`, `PerfFormat`) and `hint/MenuHint`. `StreamChromeRoot` draws the chrome and `StreamingLayer` draws the overlay and the handle. Strings are in `res/values/` only, in English.
- `host/`: `StreamChromeHost` is a `ComposeView` that `Game` adds over the stream view with `addContentView`. It draws with the `BorealisLook` that `Game` gives it, read once when the stream starts (`StreamSessionFactory.look`), so a change of a setting shows in the next stream. Its modes are IDLE, OVERLAY, DOCKED, MODAL and HIDDEN. Idle takes no focus, touch or motion. Modal takes them all. Hidden (picture in picture) takes nothing. `InputRoute` decides, from the mode, whether a key or motion event goes to the chrome or to the PC, and `HeldKeys` tracks the keys sent to the PC so that they are released when the chrome takes the input.
- `input/`: `MenuChordDetector` opens the menu when Select and Start are held for one second. It arms only from a clean start: once a button other than Start and Select has been held, it does not arm again until every button has been let go, so what is left of the quit combo (Start and Select, when the bumpers go first) opens no menu and sends no Guide tap. `ChromeChord` closes the open panel with the same chord. `GuideChord` sends a Guide tap when Start and Select are released early on a pad without a Mode button. `QuitCombo` (Start, Select and both bumpers held, then everything let go) and `StartHold` (Start let go after a long hold turns the gamepad mouse on or off) follow the button reports of a pad that reports its whole button state instead of key events. The Start hold toggles nothing while a quit combo is pending, on a USB-driver pad and on a system pad (`pendingExit` in `ControllerHandler`). `HeldThroughCapture` (`CaptureEnd` and `HeldSinceCapture`) tells the presses that began before the chrome gave the input back, so that they do nothing until the key is let go. `PointerMotion` turns a stick into the moves of the gamepad mouse, scaled by the speed setting, the session factor and the precision button. `GamepadChrome` is what the chrome asks of the gamepad handler (`ControllerHandler` implements it): captured, mouse emulation, pointer speed. `UsbChromeInput` turns the buttons and the left stick of a USB-driver pad into the keys the chrome navigates with and sends them to a `ChromeKeySink` (`UsbChromeKeys` maps the buttons).
- `keys/VirtualKeys`: the chords of the Send keys row and of the keyboard shortcut row, with their Windows virtual-key codes and modifiers.

Input routing:

- In MODAL mode the chrome takes the keys, except the volume and media keys, and the motion events. A hardware Escape acts as Back.
- In the other modes the stream keeps the keys and the touches. A docked keyboard takes no focus, so physical keys still go to the PC.
- The keyboard type is decided when the keyboard opens: docked on a phone with no game controller connected (`StreamChromeHost.dockedKeyboard`, `StreamPhase.Streaming.dockedKeyboard`). A pad held by the USB driver counts as connected.
- `StreamChromeHost.dispatchUsbPadKey` leaves touch mode before a key of a USB-driver pad while the chrome is modal.
- While the Android keyboard is open, a gamepad's D-pad, Enter and Back go to it, not to the PC (`ImeKeyGate` in `:app`).
- Back opens the menu while the stream runs, closes an open panel, leaves while the stream starts or after a failure, and cancels the conflict question.

`Game` wiring: `Game` extends `ComponentActivity`. `StreamSessionFactory` in `:app` builds the session, and `GameStreamActions` in `:app` implements `StreamActions` on the connection. `Game` forwards the stage, retry, conflict, failure, connection and performance events to the session. The manifest opts `Game` out of predictive back, so that the Back key reaches `onBackPressed` (`BackOptOutTest`).

Tests: `StreamSessionTest`, `StreamSessionChromeModeTest`, `StreamBackTest`, `StreamChromeHostTest`, `InputRouteTest`, `MenuChordDetectorTest`, `GuideChordTest`, `StreamKeyboardTest`, `KeyboardLatchTest`, `InGameMenuTest`, `MenuHandleTest`, `ConnectionErrorScreenTest`, `StartingScreenTest`, `ConflictDialogTest`, `StreamChromeHostLookTest` (the look), `StreamTalkBackTest` and `StreamAccessibilityChecksTest` (the screen reader and the Accessibility Test Framework). Roborazzi references are in `src/test/screenshots/` (see [building](../../../docs/development/building.md#screenshot-tests)).
