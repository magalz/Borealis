# Release policy

How Borealis versions, signs and distributes releases. The step-by-step
procedure is in [../development/release.md](../development/release.md).

## Versioning

- Semantic Versioning 2.0.0, **per app**. Today there is one app: Android.
- Pre-1.0 (`0.y.z`), minor versions may contain breaking changes; this is
  called out in the changelog.
- Pre-releases would use SemVer suffixes (`android-v0.3.0-rc.1`), but the
  release workflow does not support them yet (the version derivation skips
  them), so only plain `android-vX.Y.Z` tags are released.
- `versionName` and `versionCode` are derived from the
  `android-vMAJOR.MINOR.PATCH` tag by the Borealis convention plugin in
  `apps/android/build-logic`, never by editing upstream files:
  `versionCode = MAJOR * 1_000_000 + MINOR * 1_000 + PATCH`. Untagged builds
  use `0.0.0-dev`.
- Each app has its own tag namespace. Android tags are `android-vX.Y.Z`. The
  tag is the single source of truth for the version; no commit is made only to
  bump a version.
- `core/` is versioned as part of the app that ships it until it is published
  on its own.

## Changelog

- Generated by git-cliff from Conventional Commits, using
  [cliff.toml](../../cliff.toml), in Keep a Changelog sections.
- Only plain `android-vMAJOR.MINOR.PATCH` tags are considered; merge commits
  are skipped; `sync:` commits appear under "Upstream".
- Release notes on GitHub are generated by the release workflow from the
  commits since the previous `android-v*` tag (the first release starts at the
  Moonlight import commit `f397cda5`). No `CHANGELOG.md` is committed.

## Build and signing

- Releases are built by CI from a tag, never from a developer machine. The
  tag must be on a commit reachable from `main`.
- The workflow (`.github/workflows/release.yml`) has two jobs. `build` has no
  secrets and produces unsigned artifacts. `publish` signs, verifies,
  attests and creates a **draft** GitHub Release; it runs only in the GitHub
  Environment `release`, which requires manual approval by the owner.
- Release tags are protected: a repository ruleset on `android-v*` limits
  creating, updating and deleting them to the owner, and the `release`
  environment accepts deployments only from `android-v*` tags. With a single
  maintainer, "Prevent self-review" stays off on the environment, otherwise
  nobody could approve. The unsigned build artifact is kept for 30 days.
- The signing secrets are environment secrets of `release`:
  `BOREALIS_KEYSTORE_BASE64`, `BOREALIS_KEYSTORE_PASSWORD`,
  `BOREALIS_KEY_ALIAS` and `BOREALIS_KEY_PASSWORD`. The keystore is decoded to
  a temporary file that is destroyed at the end of the job, even on failure.
- The APK is signed with `apksigner` (v2 and v3 schemes) and the AAB with
  `jarsigner`; both signatures are verified before anything is published.
- One owner-held signing key is used for every channel (and as the key for
  Google Play App Signing). A separate upload key is used for Google Play.
- Signing keys never live in the repository, in workflow files, or in logs.
- Reproducible builds are deferred until after 1.0.

## Supply-chain artifacts

Each GitHub Release attaches:

- The signed APK (universal, all ABIs; per-ABI splits are not built yet) and
  the signed AAB for stores.
- `SHA256SUMS`, the SHA-256 checksums of the signed APK, the signed AAB and
  both SBOMs.
- Two CycloneDX SBOMs (JSON): the Gradle dependencies of the release APK
  (generated by the build) and the native components Gradle cannot see
  (`apps/android/sbom/native-components.cdx.json`, maintained by hand with
  every upstream sync or native dependency change).
- GitHub build-provenance attestations for the APK, the AAB and both SBOMs,
  verifiable with `gh attestation verify`.

## Distribution channels

| Channel | Notes |
| --- | --- |
| GitHub Releases | Primary. Also consumed by Obtainium. |
| Google Play | Uses Play App Signing; uploads signed with the upload key. |
| Amazon Appstore | For Fire TV and Fire tablets. |

Store uploads are manual at first and are automated later. All channels ship
the same version from the same tag. A version is not published to a store
before it is published on GitHub Releases.

## Compatibility

Each release notes the compatible LuminalShine versions and the Moonlight
version it is based on (see [upstream-sync.md](upstream-sync.md)).

## Hotfixes and withdrawals

- A hotfix is a normal PR to `main` followed by a patch release.
- A release with a serious defect or vulnerability is superseded by a patch
  release; the advisory process in [SECURITY.md](../../SECURITY.md) applies.
  Only the latest release is supported.
